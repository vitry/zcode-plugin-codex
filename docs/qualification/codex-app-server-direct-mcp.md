## 7. Limitations

- This stage measured Host provenance and the generated schema surface only; no live `mcpServer/tool/call`, handler entry, turn-state, or lifecycle observation was made in this run. Every gate decision in later tasks requires the bounded real-host campaigns of Tasks 3–6.
- Documentation pages are moving targets; the rechecked App Server and MCP pages redirect to `learn.chatgpt.com`. Schema presence of a method does not identify the release that introduced it, nor prove runtime behavior.
- The schema digest is exact for this machine's measured run; regenerating on another platform or version will differ and requires a new evidence set.
- File-based handler provenance in `tools/direct-mcp-probe/` is per-record MAC-authenticated and TAMPER-EVIDENT, not tamper-proof. The driver generates a per-run random 256-bit capability secret and passes it to the spawned server executable via spawn-time env, held only in that process's memory; the server writes the owner registration carrying the run's handler-owner pid plus the secret's salted digest (never the secret), and MACs every handler-side record it appends (HMAC-SHA256 over the canonical record, sequence included). The shared log primitive accepts handler-side kinds only from the registered owner process presenting the secret, and the driver's verify-then-reduce gate (`reduceDirectProbeLog`) fails closed with `PROBE_OWNER_INVALID` unless the owner file matches the driver's expected secret and server pid AND every handler record's MAC verifies — so appended-forged, swapped-owner, replayed, or tampered handler records are never reducible as handler evidence. The trust boundary is "processes holding the driver-generated secret" (the driver and the spawned server); same-user processes without the secret cannot produce reducible handler evidence. Server instances also maintain a process-wide handler commit state per run: a new instance for a run whose current seal head does not extend the process-held commit refuses creation (`PROBE_STATE_DIVERGED`), so a rolled back or diverged log+journal pair cannot be laundered by re-instantiating the server. Residual window (recorded): a same-user process restoring an intermediate historical (log, journal) pair after all writer processes have exited and before the driver's final anchored reduction is not detectable from the files alone — the driver's in-memory final anchor is the detection boundary. A driver process that itself fabricates evidence is out of scope (its artifacts are the evidence). Recorded as an instrument limitation per the evidence discipline.

### 10.1 Active-turn mechanism research (bounded; recorded attempts)

### 10.2 Ordering rules and the synthetic admission gate (local fixtures, no host)

The ordering rules live in `tools/direct-mcp-probe/identity.mjs` (pure, no IO). `classifyDirectIdentitySample` classifies one sample from the durable records' shape alone: `binding-observed` requires the exact expected turn — learned independently by the driver, never from request metadata — to be observed ACTIVE in ordered `turn-state-observed` records both BEFORE and AFTER the durable handler-entry sequence, AND a matching, independently COMPARABLE thread AND turn metadata candidate (per-run salted) corroborating the same identity. The `innerSessionId` candidate is recorded presence evidence but is never comparable (the host exposes no learnable session identity), so a session-only — or otherwise partial — sample stays `correlation-only` and can never claim the metadata-to-turn binding or feed G2's proven branch. Idle and completed-thread samples classify `correlation-only` (matching hashes are correlation, never authority); a turn that disappears between the pre-read and the post-read classifies `inconclusive`; a usable candidate that contradicts the learned identity classifies `mismatch-observed`. The classifier takes NO diagnostic label input, so a matching label can never upgrade a sample.

The authorization bridge is implemented as a CANDIDATE, not a fact: `createDirectIdentityPreparationStore` models the existing preparation store's consume-time discipline (exact operation/thread/turn binding, workspace/permission/executor/adapter equality, expiry, cancellation, and ONCE-ONLY atomic consume bound to the unique preparation RECEIPT issued at authorize time) over per-run salted hashes. Admission resolves strictly by receipt — thread/turn identity alone never selects a preparation, so a replayed earlier request can never consume a newer same-turn reauthorization: the spent original's receipt reports `preparation-consumed` while the newer preparation stays unconsumed, and an unclaimed replay fails closed (`preparation-receipt-missing`). The positive fixture demonstrates the admission MECHANISM only, through the fixture-internal trusted-caller path (`probe-driver-own-thread`); a request that merely echoes host metadata without a receipt is rejected (`preparation-receipt-missing`); a race test proves a late turn-A call cannot consume the distinct turn-B preparation (claimed-id mismatch surfaces `turn-mismatch`, and B's preparation stays consumed exactly once by B). Wrong-thread, stale-turn, duplicate, cancelled-authorization, expired, untrusted-caller, and host-observation-not-active fixtures all fail the gate with closed reason codes.

## 12. Task 5: lifecycle settlement mechanism (local, synthetic worker)

The lifecycle stage characterizes what happens to a held, accepted downstream call when its lifecycle triggers fire. Its instrument is the disposable server's `hold_direct` tool: the handler's first durable action is `handler-entered` (Task 2), it then persists `hold-started` carrying the synthetic worker's `workerHash` — the durable worker claim — and only then blocks. Settlement is decided once, written as `handler-settled` and `worker-settled` in order, joined to the held call nonce, and confirmed by durable reads before the pending-hold registration drops; a failed or ambiguous append is retried by the durable-read-driven reconciliation inside a bounded budget, and whatever cannot be confirmed stays registered for the disconnect pass. The synthetic worker emulates a probed command; it is never a real job.

Two probe-owned mechanics were added for this stage, both test-scale and bounded:

- `holdMs` (optional `hold_direct` argument, bounded integer): the synthetic worker completes on its own after this duration — the normal-completion path whose durable outcome is `completed`.
- `DIRECT_PROBE_HOLD_SAFETY_DEADLINE_MS` (spawn-time env, forwarded through the disposable descriptor's `env_vars`): a per-server forced-settlement ceiling that settles any still-undecided hold with the `safety-deadline` outcome. This is the MECHANISM-ONLY injected emulation of the production 100-hour ceiling; it is labeled mechanism-only wherever it is recorded and is never evidence that a tested host supports a 100-hour tool call.

### 12.2 The local case state machine and the G3 gate

`classifyDirectLifecycleCase` (pure, in `lifecycle.mjs`) classifies ONE case from the durable records inside the case's own record window plus the authenticated reduction — downstream settlement is never inferred from RPC outcomes or turn status (the one RPC reading is the observation-only placement's WAIT-ENDED witness, which establishes that the wait call itself concluded — never a worker settlement). Its closed classifications: `settlement-observed` (durably observed terminals matching the command expectation, with the settled `workerHash` joined exactly to the held worker), `behavior-confirmed` (the observation-only placement confirmed: the caller cancellation was durably ACKNOWLEDGED for the call, a specific wait-ended observation exists — the wait call answered or was rejected; an `rpc-observed` `not-observed` is an indefinitely pending wait and records `settlement-unproven` (`wait-ended-unobserved`) — AND the sentinel's CLASSIFICATION RESULT is conclusive. Since the decision-order adjudication no per-call sentinel classification is conclusive (a caught sentinel is the `sentinel-caught` mismatch; every unproven classification records `settlement-unproven` with its own reason), behavior-confirmed is reachable only for a case with NO sentinel at all — the infrastructure triggers carry their own `infrastructure` scope and never enter the observation branch, so under the current expectation table per-call observation cases honestly record the sentinel's unproven reason instead), `expectation-mismatch` (the durable observation contradicts the command expectation — e.g. `status-target-killed` (including a race that settles an observed job: the contradiction outranks every unprovability state), or an unrelated sentinel cancelled by a per-call trigger, `sentinel-caught`), `settlement-unproven` (the case demanded a decision and no durable terminal exists — `worker-never-settled`), `not-sent` (a prerequisite was missing: request not sent, no durable handler entry, no durable `hold-started`, unconfirmed exact turn for an interrupt, or an honestly not-sent trigger), and `not-observed` (no dispatched request). Prerequisites are enforced in order: a trigger may act only after the durable `hold-started` exists, and an explicit interruption may be sent only when the driver independently confirmed the exact active turn.

`classifyDirectGateG3` (driver.mjs) pins the plan's rule that an interrupted turn with a still-running worker FAILS G3 — that reason takes precedence over every other. `proven` further requires the reconciliation assessment not rejected, no expectation mismatch, no settlement-unproven case, every required trigger covered by a case actually sent (a `not-sent` interruption is a missing prerequisite, `interrupt-case-not-sent`, never a pass), and every case classified `settlement-observed` or `behavior-confirmed`.

### 12.3 Reconciliation strategy assessment (plan Task 5 Step 5)

`assessDirectReconciliationStrategy` assesses the durable stop-intent/supervision-style reconciliation candidate — the one actually implemented in the disposable server (bounded-retry, durable-read-driven settlement of registered holds). The synthetic worker tests prove exact ownership (the settled `workerHash` joins the held worker) and bounded settlement (retry budget, idempotent terminals confirmed by durable reads), so the strategy is accepted as demonstrated WITH LIMITS rather than rejected: its coverage is transport/process loss visible AT the server (disconnect, respawn), and it cannot settle anything when no durable writer survives. The real-host evidence below sharpens this: abrupt host loss did NOT leave the strategy unreachable (the disposable server survives its host and reconciled durably), while upstream cancellation that the host does not propagate (client disconnect, configured tool timeout) leaves the worker running past the bounded window — outside the strategy's reach by construction. The assessment never upgrades G3 by itself; it only records under which conditions the tested strategy is acceptable.
