## 5. Candidate entry sketches (Task 1 output; not selected, not frozen)

Each sketch states source of user authority, execution owner, wait owner, result route, cancel route, and its first discriminating test. Unknowns are marked unknown.

### 5.1 Candidate U — UserPromptSubmit `mcp_tool` hook

- Sketch: fixture-local UserPromptSubmit `mcp_tool` hook calls a model-hidden capture tool on the owning session; the hook template expands host event fields (`turn_id`, `session_id`, `prompt`) so the capture tool can log what the host attested at turn start.
- Source of user authority: the host itself (hook dispatch injects owning-session `threadId` and host event identity); the USER authority for any work remains the Companion's own later Root preparation — NOT available at this event. Unknown: whether a preparation can legitimately be created before Root's semantic selection runs (spec R2 says parsing the prompt in a hook must not replace it).
- Execution owner: the owning session's hook executor calling its own MCP runtime (`hook_mcp_executor.rs`), synchronously, concurrently with any other same-event hooks.
- Wait owner: the hook call itself, bounded by `min(hook timeout, server tool timeout)`; a long hold here blocks the user turn before the model starts. Unknown: host-side consequences of a turn-start hold (steering, elicitations).
- Result route: text-only — plain-text output becomes additionalContext injected before first sampling; handler errors are Failed (fail-open, turn continues). No lossless terminal route exists at this event.
- Cancel route: user interrupt of the turn while the hook is pending. Unknown: whether the hook call is cancellable at that boundary (Task 6).
- First discriminating test: install the fixture hook with a two-second capture tool and NO other hooks, submit one prompt, and check (a) the capture tool receives host `threadId`/`turn_id` metadata and (b) the model's first sampling request contains the hook's returned text. If the hook's text never reaches the first sampling input, or fires more than once per prompt, the entry is falsified cheaply.

### 5.2 Candidate P — PreToolUse `mcp_tool` hook (matched to the foreground tool)

- Sketch: a PreToolUse `mcp_tool` hook matched to the exact shell/foreground tool name fires inside tool dispatch, after the model has issued an already-prepared invocation; the hook template expands `tool_input`/`tool_use_id`/`turn_id` into a capture call that records the exact invocation boundary.
- Source of user authority: still unresolved — `tool_input` is model-authored, and event identity is host-generated; neither is invocation authority. Unknown: any supported per-invocation discriminator deliverable to the hook.
- Execution owner: the owning session's hook executor, synchronously inside the tool dispatch path, before the real tool handler runs.
- Wait owner: the hook call, bounded by `min(hook timeout, server tool timeout)`; a hold here delays the actual tool the model asked for. Unknown: interaction with the 30 s initial-exec yield if the matched tool is the shell tool itself.
- Result route: text-only additionalContext; `decision: block` (command hooks) or blockable outcomes can stop the tool; `updated_input` rewrite exists but is not a result route. No public terminal route.
- Cancel route: turn interrupt aborts the dispatch task (tool-level cancellation observed in source); the pending hook future is dropped with it.
- First discriminating test: with a two-second capture hook matched only to the foreground shell tool, run one shell invocation and verify exactly one hook dispatch per tool call carrying the real `tool_use_id`, and that the tool handler still executes afterward. A hook-budget-length hold of the tool handler is EXPECTED, not a falsification signal: the host awaits `run_pre_tool_use_hooks` synchronously inside tool dispatch before the handler executes ([tools/registry.rs#L602-L654](https://github.com/openai/codex/blob/67727e7cf114cf3e1b71db368d74b24e32f6cb12/codex-rs/core/src/tools/registry.rs#L602)). Falsify only when (a) the handler hold exceeds the declared hook budget by a wide margin or never terminates (an uncapped hold), (b) the hook never dispatches or the tool handler never executes, or (c) the hook fires for tools other than the matched one (aliasing).

### 5.3 Candidate O — PostToolUse `mcp_tool` hook

- Sketch: a PostToolUse `mcp_tool` hook matched to the foreground tool fires after the tool's successful output, receiving `tool_input` and `tool_response`; the hook could only ever observe or supplement completed work, never launch it (any launch would duplicate the original command's work).
- Source of user authority: none beyond observation — the work is already done by the original command; a hook here cannot claim authority for new work. Unknown: none expected to be found; this candidate is expected to fail the authority question by construction.
- Execution owner: the owning session's hook executor after the tool output is produced.
- Wait owner: the hook call (same timeout join); holding here delays the tool result's return to the model.
- Result route: feedback_message / additionalContext only; no input rewrite, no public terminal route.
- Cancel route: same turn interrupt path as above.
- First discriminating test: with a two-second capture hook on the foreground tool, verify the hook sees the real `tool_response` exactly once per completed call and that a second launch of work is neither triggered nor needed. If PostToolUse proves to fire on background/partial outputs as well (duplicate events per invocation), it is falsified as a deterministic single terminal boundary.

Cross-candidate note for Task 4: because same-event hooks run concurrently, a delayed synthetic authority publisher can race any of these candidates; declaration-order re-sorting is not a fix, and each candidate must be assessed against the real event boundaries above.
