# Run Rescue background in a session-bound runner

Normal background Rescue (`--background`, or the complexity inference selecting background) executes in one session-bound Detached Rescue Runner. The Rescue Child validates Host authority, durably reserves the exact job with its bounded private execution input, spawns one thin detached runner, awaits only the operating system's successful-spawn event, and returns the Queued Rescue Acknowledgement; the child may then exit. The runner claims the already-reserved job through the existing worker-lease CAS and executes it through the same shared execution path as attached work. Foreground Rescue remains attached to its Rescue Child and returns the full terminal result; this decision changes only background placement.

Queued is accepted-only. The acknowledgement confirms that the job and its private execution input are durably accepted for execution; it never proves that the runner claimed the job, started execution, opened ZCode, sent a turn, or remains alive, and it never finalizes a completion marker. A deterministic spawn or setup failure before any accepted turn settles the still-queued job through the pre-start failure policy instead of returning queued; hard runner death before claim leaves the job queued with no automatic retry.

Completion uses pull and PromptSubmit, not a live notice. Status and Result are the authoritative pull interfaces. The next `UserPromptSubmit` discovers an unread terminal job through the existing notification claim/finalize machinery and presents a bounded, task-free notice; delivery claims prevent two concurrent deliveries of the same job, while a crash after output but before marker finalization remains retryable. The plugin does not promise transactional exactly-once delivery to the Host UI. Enqueue delivery never marks a completion notice as delivered, and no new Host callback, observer child, or notification daemon is introduced.

Exact binding and the one ledger are retained. The existing job/binding/receipt system remains the single authoritative ledger; the runner is placement, not authority — its PID and lease identify the executor only while it holds the worker lease, and never authorize a turn. Host lifecycle epochs, the immutable SessionEnd receipt, exact child/operation/anchor/ZCode-session binding, permission equality, first-writer-wins terminal state, uncertainty retention (the Writable Guard), and the Rescue Lifecycle Reconciler of ADR 0019 as the single lifecycle seam all continue unchanged. ADR 0020's exact process-tree termination and uncertainty principles now apply to writable detached Rescue: SessionEnd and explicit cancel stop the exact remote turn, then terminate only the proven marked runner tree, and local death never upgrades uncertain remote state.

Windows runner termination is descendant enumeration with broker-subtree exclusion. The invariant that the separately managed ZCode broker must never be killed as a runner descendant conflicts with `taskkill /T`'s unconditional tree walk, so production Windows termination of a marked runner enumerates its living descendants, excludes the managed broker subtree, and terminates the remainder; when descendant identity lookup fails it fails closed to terminating only the recorded runner PID. This consciously narrows the older "Windows `taskkill /T`" wording retained by earlier lifecycle decisions; on POSIX and Windows alike it never signals a PID whose worker lease is free. Native Windows and Linux CI runs of `tests/integration/true-background-rescue.test.mjs` remain a release condition and are pending until a native run exists.

This decision supersedes only the conflicting clauses of [ADR 0017](0017-deliver-background-completion-through-the-host.md) and [ADR 0018](0018-use-host-managed-session-bound-execution.md) identified above and cross-linked there. ADR 0018's remaining decisions — single ownership, exact binding, SessionEnd resumability, uncertainty retention, and non-destructive historical compatibility — and ADR 0017's durable single-delivery rules remain in force, as do ADR 0019 and ADR 0020 in full. Historical detached Rescue jobs and the read-only detached Review paths keep their existing behavior.
